# Matrice des exigences et preuves MVP-001

Ce document complète la [matrice des preuves P0](../quality/p0-evidence-matrix.md)
et ne la remplace pas. La matrice P0 détaille les preuves par story US-001 à
US-006; celle-ci suit les exigences transversales ACT-01 à ACT-13 du
brief de projet accepté
et les relie aux sections et stories pertinentes. Les références d'état sont
celles des artefacts cités, relus dans le snapshot `a9a463cc` lorsqu'indiqué
dans le registre de traçabilité du 2026-10-20. Elles ne signifient pas que les
tests ont été rejoués dans ce checkout.

## Lecture des colonnes

- **Décision owner** rapporte uniquement une décision explicitement attribuée
  au responsable dans une source; sinon la décision reste non documentée ou
  ouverte.
- **Source documentaire** cite l'artefact et son statut littéral quand la
  source en donne un.
- **Test exécuté** rapporte le résultat déjà consigné, avec date et SHA s'ils
  sont disponibles. « Non établi » signifie qu'aucune exécution pertinente
  n'est citée par les sources consultées.
- **Rendu observé** sépare les captures historiques du rendu actuel. Une
  maquette statique n'est pas un rendu navigateur.
- **Approbation** n'est renseignée que lorsqu'une approbation explicite et sa
  portée sont documentées. Une revue limitée ne vaut pas approbation globale.
- Les owners entre parenthèses sont des rôles proposés par les sources, pas
  des affectations nominatives. Les actions dépendant d'une personne ou d'un
  environnement externe restent ouvertes.

## Portée et état

Les statuts ci-dessus reproduisent ceux des artefacts cités; ils ne ferment
aucune action humaine, juridique, de conformité, d'audit ou dépendant d'un
environnement externe. Le statut global reste `needs-review`, et
`design-readiness.md` reste `Status: review`. La matrice ne remplace pas les
détails par story, commandes, résultats et limites conservés dans
[`p0-evidence-matrix.md`](../quality/p0-evidence-matrix.md).

## Demande owner additionnelle : identité de build

Le 2026-10-20, le responsable a demandé un système de versionnement visible
pour comparer l'application Docker locale au rendu observé dans le navigateur,
avec une mise à jour coordonnée du README et du menu du pseudo à chaque
modification ou correction. Cette demande améliore la traçabilité de build mais
est distincte des exigences ACT-01 à ACT-13 du cahier accepté; elle ne doit pas
être silencieusement ajoutée aux critères de clôture MVP-001. Elle est suivie
dans l'issue [#418](https://github.com/Krapaud-Labs/Skkup/issues/418), visible
dans le projet GitHub Skkup, colonne « Backlog validé ».

Baseline de conception à faire relire : générer à la construction une identité
reproductible contenant au minimum la version produit et le SHA du commit
source; l'afficher comme texte accessible dans le menu du compte; documenter
dans les README concernés la source de vérité et la procédure de comparaison.
Un build local issu d'un arbre modifié doit être distinguable d'un build propre
du commit, sans exposer de secret ni de donnée utilisateur. L'implémentation et
les valeurs exactes de versionnement restent à spécifier après la gate design.

État observé : aucun identifiant de build n'apparaît dans le menu pseudo du
Docker local; le rendu et les sources visibles du checkout ne peuvent donc pas
être rapprochés de manière vérifiable. **Action :** faire relire les critères
de l'issue #418 puis implémenter avec tests build → menu → README après
approbation de conception. Cette demande n'est pas déclarée implémentée.
